Proposed interaction model

One review header, a compact mobile footer

  • All sizes: full-width blue strip inside the artifact; comments visibility/count, clearly indicated commenting mode, and send state/action. No floating pill.
  • Narrow or short view: selected target/quote stays visible above a compact bottom composer. Open existing comments in the same footer surface; expand only when needed.
  • Wide view: keep an anchored discussion popover when there is room. A persistent desktop rail can be a later choice, not a prerequisite.
  • Keep local comment creation distinct from sending the review to the bot. Show unsent / sending / sent / failed / uncertain status, and disable duplicate sends.
  • Reserve header/footer space rather than covering sticky headers, slide navigation or the selected target. Respond to the artifact’s viewport, not the outer desktop window.

Library guarantees vs skill guidance

Library guarantees

Responsive header and comment surface; focus and keyboard handling; minimum hit areas; draft lifecycle; mode/visibility consistency; clear review numbering; bounded overlays; safe-area and visual-viewport support; accessible labels and status presentation.

Expose layout insets and a small typed status/action interface. Avoid forcing bots to reproduce this UI independently.

Host + skill responsibilities

Choose readable artifact layouts; preserve stable target IDs; label appropriate review units; keep annotation chrome outside transformed/scaled slides; offset sticky app headers; define scroll roots and slide navigation; provide a full manifest for temporarily unmounted targets.

Host still owns persistence, authorization, revision conflicts, idempotent sending and real delivery truth. The library must never claim “sent” without host confirmation.

Implementation plan for approval

  1. Responsive shell first. Add the blue header and narrow-view footer with explicit layout insets. Keep current controlled document API, anchoring, and desktop gestures intact. Add responsive focus, safe-area and visual-viewport handling; draft preservation; accessible SVG controls.
  2. Touch and artifact integration. Make scroll vs image-region selection deliberate; add an explicit on-screen route to annotate native text selection. Extend host navigation/manifest support for decks and update INSTRUCTIONS.md with tested spec/UI/deck recipes. Reconcile existing README/product-guide behavior mismatches as part of the change.
  3. Regression and physical-device QA. Run the same fixtures against baseline and candidate. Assert no header/footer overlap, visibility of target and actions, draft preservation on resize/orientation/keyboard, touch scrolling, reply/resolve behavior, correct send states and stable anchors. Validate real iOS Safari and Android Chrome before release.
  4. PR and rollout. Push the reviewed implementation and tests only after alignment. Changes affect the shared library and reference host/skill, not the PromptQL console. Already-generated apps need a rebuild/update to consume the new version.

Performance and blast radius

Keep document-coordinate overlays and existing “measure only needed targets” behavior. Use a shared resize/visual-viewport listener with animation-frame scheduling; do not add per-pin scroll listeners or measure the entire document on every keystroke. Compare baseline/candidate frame timing during scroll and with a populated fixture. Keep responsive UI state out of serialized annotation documents.

The host provides layout offsets and delivery callbacks; no new platform permissions or backend changes are needed for the first responsive-shell phase. Deck navigation metadata is an additive host contract and should be designed separately from persisted comment references.
